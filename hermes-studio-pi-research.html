一个AI中台，一台极简引擎

你已经在用 Hermes Studio 统一管理 Agent、用飞书编程；也用过 Pi 跑项目但觉得"太简单"。这份调研挖出了 Studio 里你还不知道的能力，也看清了 Pi 的"极简"其实是设计而非缺陷。

数据来源：Hermes Studio 本地 472 REST 端点实测 + 开源社区实践 + 全网案例 · 2026-09
THESIS 01 · 定位

Hermes Studio 是指挥中枢（统一管理、调度、看板、跨 Agent 编排），Pi 是单兵引擎（极简执行、上下文工程）。两者不是竞品，是上下两层。

THESIS 02 · Studio 挖掘

你现在只用了 Studio 的冰山一角：472 个 REST 端点、52 个能力模块。Coding Agents、看板调度、LAN 远程设备、工作流编排——这些才是"AI 中台"的真正富矿。

THESIS 03 · Pi 破译

Pi 的"太简单"不是不够用，而是刻意少内置、把能力留给你长。它的核心不是 4 个工具，而是 Extensions / Skills / AGENTS.md / Dynamic Context 这套上下文工程。OpenClaw 就长在 Pi 之上。

「你还不知道」的能力清单

🤖

Coding Agents

未用

直接在 Studio 里安装、配置、运行 Claude Code / Codex 这些"外部编码 Agent"——把它们当下属挂到中台调度。

→ /api/coding-agents/{id}/install

📋

Kanban 看板赋能

未用

把任务建成卡片，指派给不同 Profile 的 Agent 去执行，支持批量派发、链接、统计、诊断——真正的多 Agent 任务生产线。

→ /api/hermes/kanban/dispatch

🔀

Workflows 编排

未用

跨 Agent 的图形化工作流，节点级审批、断点重跑、定时调度、一键运行——把重复的多步流程固化成自动化流水线。

→ /api/studio/workflows

🖥️

Devices / LAN 远程设备

未用

局域网扫描、配对、远程终端、执行命令、上传下载文件——甚至能管 MCU 微控制器设备和固件分发。一台 Studio 管多台机器。

→ /api/devices / {id}/connect

💬

Group Chat 多 Agent 群聊

未用

建一个多智能体群，里面多个 Agent 各自扮演角色、互相协作讨论——让 A、B、C 三个 Agent 共商一个方案，不是你串行调度。

→ 61 个群聊端点

🧩

MCP 工具注册

已部分用

Studio 里直接管理 MCP server 与工具，把外部系统（你的 Metaso、飞书文档、Sales DB）注册成中台可调用的工具。

→ /api/mcp

🛡️

Write Gate 写审批

未用

对 Agent 写操作（改文件/写库）做审批把关，适合"让 Agent 自动跑、但关键写入要人确认"的合规场景。

→ /write-gate

📤

Social Messages 外发

未用

统一向外发消息到多处社交平台——自动简报、监控告警集群推送的多渠道分发口。

→ /social-messages

判断一个 AI 中台值不值，不看它内置了多少功能，而看它能不能把「多个 Agent」编成一支「有分工的队伍」——有的做规划、有的做研究、有的执行、有的交付。Studio 的看板、工作流、群聊就是干这个的。

Pi Agent · 极简不是缺陷，是设计哲学

Pi 是 Mario Zechner 用 TypeScript 写的极简终端编码 Agent（只有 ~418 行核心、90 词 system prompt、4 个内置工具）。你"跑项目觉得太简单"，恰恰是因为把"极简"当成了"功能少"，但它真正卖的是"可控性"。

Pi 的 4 层扩展与上下文工程（这就是"把简单搭复杂"的钥匙）

1
AGENTS.md · 项目级上下文

把项目怎么装、用什么工具、测试在哪、架构文档在哪——写成 AGENTS.md（兼容 CLAUDE.md），Pi 启动时自动加载，提示词被自动增强。

~/.pi/agent/AGENTS.md

2
Skills · 按需加载的能力包

实现 Agent Skills 标准，渐进式披露：启动只放名字+描述，任务匹配时才加载全文。可复用 Claude Code / Codex 的技能。

~/.pi/agent/skills/my-skill/SKILL.md

3
Extensions · TypeScript 长出能力

用代码写扩展，可访问工具/命令/快捷键/事件/整个 TUI。子代理、计划模式、权限门控、SSH 执行、沙箱、MCP 集成全靠它。官方 50+ 示例。

自定义 tools / permissions / subagent

4
Dynamic Context · 动态注入上下文

扩展注入消息、过滤历史、接 RAG、长期记忆；SYSTEM.md 替换默认提示；接近上限时自动压缩。

SYSTEM.md / Compaction / Prompt Templates

为什么 Armin Ronacher（Flask 作者）"上瘾"到几乎只用 Pi？因为当 Agent 的骨架足够干净、足够透明，你才能精确地控制它的上下文——而上下文，恰恰是 Agent 时代最稀缺的资源。堆一百个工具不如把上下文喂准。

Hermes · 多 Agent 分工战队

建一个"总管" Profile 当调度核心，统一协调多个下游 Agent，靠超长上下文跟踪催办。核心：把单 Agent 升级成有分工的小型数字工作室。

→ profile 隔离 + 总管调度
💬

Hermes · 飞书多 Agent 群协作

在飞书群 @ 不同的 Agent（后端/前端/总控各一角色），每个 Bot 配不同 Profile + Skills，由总控统一调度。最贴合你的日常——飞书群就是指挥台。

→ 群内多 Bot 分工
⏰

Hermes · Cron 自动简报

用自然语言告诉 Agent 想要什么，自动生成 cron 配置：每天定点搜竞品/行业/融资，整理成简报推飞书。你已经在跑，这是被验证的成熟玩法。

→ cron 调度 + 推送

PART 04

对你有用的落地建议

基于你的实际场景（飞书编程 + 多个 Agent + 知识中台），挑三条最值得立刻试的。

①
把 Studio 从"管理"升级到"调度"

你已用 Studio 统一管理 + 飞书编程。下一步把它当指挥台用：用 Kanban 看板把任务指派给你的多个 Agent（阿森/销售助理/爱马仕），用 Workflows 把重复的"采集→处理→推送"固化成自动流水线，用群聊让多个 Agent 共商一个方案。

②
别再用 Pi 干它不擅长的事

Pi 的极简适合精准、可控、上下文清晰的编码任务（单模块、可验证、贴近你 MIT 单专题流水线的思路）。复杂大项目、多 Agent 并行、飞书中台调度——这些交给 Hermes Studio，别硬塞给 Pi。两者配合：Studio 指挥，Pi 执行。

③
给 Pi 或任何 Agent 建 AGENTS.md

把项目上下文（装什么、怎么跑、测试在哪、架构在哪）写进 AGENTS.md——这是社区公认"成本最低、收益最高"的提效动作，对你所有 Agent（含 Hermes）都适用。
